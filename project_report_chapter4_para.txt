CHAPTER 4: IMPLEMENTATION

4.1 OVERVIEW OF SYSTEM IMPLEMENTATION
The implementation phase of the Campus Complaint Management System translates the conceptual designs, architectures, and database models into a fully functioning full-stack software application. The development lifecycle is structured around a modular Python Flask framework configured to process incoming web requests, validate user sessions, coordinate transactions with a MySQL database server, and render dynamic templates. The codebase is organized cleanly into server-side controllers, configuration modules, local SQL schema files, frontend styling packages, and client-side JavaScript controllers. By separating the application into these modular blocks, we achieve high maintainability, allowing individual features (such as notifications or feedback) to be modified without affecting other core functions of the portal.

4.2 COMPONENT-LEVEL CODE ORGANIZATION
The system implementation is organized into four main functional blocks within the project directories. The root level contains config.py, which defines global configuration constants including Flask session keys, file upload size limits (5MB), and primary MySQL credentials, alongside app.py, which serves as the main entry point housing all the Flask controller functions, session checkers, database query functions, and RESTful API endpoints. The database folder contains schema.sql, representing the raw DDL queries to rebuild the MySQL schema, and campus_complaints.db, which is the local SQLite database file used as a resilient fallback. The static directory is divided into a stylesheet subdirectory containing custom CSS rules for the glassmorphism theme and a javascript subdirectory containing dashboard.js, which manages interactive modal events and triggers AJAX requests. Finally, the templates folder contains separate HTML views for the landing portal, user login, student dashboard, admin console, tracking timelines, and notification logs.

4.3 ROUTING, CONTROLLERS, AND API ENDPOINTS
Backend controller functions in app.py are mapped to specific URL paths using Flask route decorators. These routes are divided into page rendering routes, which return HTML layouts generated dynamically by the Jinja2 engine, and API routes, which receive and return data in raw JSON formats. Page controllers (such as /dashboard or /admin_dashboard) first execute a role-check helper to verify if the user is authenticated and possesses the required permissions (Student, Staff, or Admin) before fetching records and rendering the matching view. API routes (such as /api/update-status or /api/dashboard-stats) handle state changes asynchronously. When a student rates a resolved issue or an admin assigns a staff member, the frontend makes an AJAX fetch request to these endpoints; the backend processes the request inside a try-except block, commits the transaction to the database, generates logs, and returns a JSON dictionary indicating success or failure.

4.4 DATABASE CONNECTOR AND HIGH AVAILABILITY FALLBACK
The database connectivity layer is designed to run reliably under dual configurations. The connection class initializes using PyMySQL to open a connection pool to the local MySQL server on port 3306. To prevent runtime crashes in case the local MySQL server goes offline, the backend code implements a self-healing database adapter. On startup, the script attempts to establish a connection to the MySQL server; if a socket exception occurs, the system logs the failure, changes its internal database adapter state, and diverts all subsequent queries to the local SQLite database file using the built-in sqlite3 library. To maintain a consistent database schema across both engines, the backend SQL queries are parameterized using standard placeholder symbols, allowing identical SQL syntax to execute correctly on both MySQL and SQLite without requiring separate query logic.

4.5 SECURITY AND DATA PROTECTION
Security is enforced on multiple layers to protect user information and prevent database vulnerability exploits. Passwords are never saved as plain strings; during student registration, the application processes the password using the Bcrypt hashing algorithm, applying a random salt and running ten rounds of key stretching to generate an irreversible 60-character hash stored in the database. Session cookies are signed with a secure cryptographic key (defined in the configurations) to prevent client-side cookie tampering. Furthermore, the application guards against SQL injection attacks by strictly using parameterized queries—using %s placeholders in MySQL and ? placeholders in SQLite—instead of string formatting, ensuring that user inputs are treated solely as data parameters and not executable code. Lastly, file uploads are validated dynamically on the backend, rejecting any attachments that exceed the 5MB size limit or carry extensions outside of the approved list (PNG, JPG, JPEG, GIF, PDF).
