CHAPTER 5: INTERPRETATION OF RESULT

5.1 SYSTEM FUNCTIONAL VERIFICATION RESULTS
The functional verification of the Campus Complaint Management System confirmed that all core user portals, data structures, and role configurations perform according to specifications. When simulating student actions, the registration and login forms successfully authenticate users, hashing passwords via Bcrypt and loading session state configurations dynamically. Testing the complaint submission form verified that inputs (including titles, description text, priority choices, and attached image/PDF files) are validated on the backend and saved with a default status of "pending". The admin dashboard accurately displays all submitted complaints, and the assignment controller correctly routes complaints to staff members. Furthermore, query results from the custom database view (v_complaint_details) verified that the system performs multi-table joins correctly, displaying human-readable values like student names and categories in place of numeric database IDs.

5.2 AUDIT TRAIL LOGGING AND WORKFLOW TIMELINES
Verification of the workflow logging system showed that the audit trail captures all complaint lifecycle transitions with high accuracy. When a status update occurs (e.g., transitioning from "pending" to "resolved"), the backend triggers database updates that write detailed logs into the complaint_logs table. Inspecting the database records after running tests verified that each log row stores the correct old status, new status, modifier ID, remarks, and exact event timestamp. In the student dashboard, this logged history is retrieved and rendered as a visual, interactive vertical timeline. This timeline updates dynamically as new actions occur, showing the student a transparent chronological flow of their grievance's resolution. This confirms that the audit trail is highly reliable for accountability and reporting.

5.3 REAL-TIME DASHBOARD SYNCHRONIZATION
The integration of asynchronous API endpoints and client-side JavaScript controllers successfully achieved real-time dashboard updates without page reloads. When an admin deletes a complaint, changes its status, or assigns a staff member, the dashboard sends an AJAX fetch request to the backend. The backend returns a JSON payload containing the updated statistics, which JavaScript uses to update the DOM elements immediately. Functional tests showed that the stats cards (Total, Pending, In-Progress, and Resolved) re-render numbers instantly using smooth incrementing animations. Additionally, the CSS donut chart, which operates on a conic-gradient style sheet background, adjusts its progress degrees and legend percentages dynamically to match the new database counts. This proves that the frontend and backend remain perfectly synchronized without requiring full window refreshes.

5.4 DATABASE FAILOVER AND TRANSACTION CONSTRAINTS
The database layer successfully enforces relational constraints and remains resilient during server interruptions. Tests on referential integrity confirmed that the ON DELETE CASCADE constraint on complaints safely deletes all subordinate records in the comment, log, feedback, and notification tables, preventing database clutter or orphaned rows. Testing the CHECK constraint on the feedback table verified that the database rejects any rating value outside of the 1 to 5 range. Furthermore, testing the high-availability failover mechanism proved highly successful. When the local MySQL server daemon on port 3306 was manually stopped, the backend automatically intercepted the connection error and redirected all incoming read and write transactions to the local SQLite backup database file (campus_complaints.db), allowing users to browse and log complaints continuously without system downtime.
